## Context

Мотивация и поведение описаны в proposal.md и specs/new-card-form/spec.md. Разведка текущей ветки main показала: NewCardForm хранит title в useState; handleSubmit уже отклоняет !title.trim() и передаёт createCard обрезанную строку. Успех мутации обновляет запрос cards и очищает поле. disabled кнопки сейчас зависит только от mutation.isPending. CSS уже содержит .button:disabled с opacity: 0.5 и cursor: not-allowed.

Выданная постановка описывает исходную ошибку курса; в этой копии проекта защита отправки уже появилась в теме 1. Её не удаляем и не выдаём за новую реализацию.

## Goals / Non-Goals

**Goals:** согласовать доступность кнопки с существующей защитой отправки, сохранив успешное добавление и очистку поля.

**Non-Goals:** изменения API, очистка ранее сохранённых данных, новая система валидации.

## Decisions

- Добавить !title.trim() к условию disabled через логическое ИЛИ с mutation.isPending. Это не требует нового состояния, учитывает пробелы и сохраняет блокировку повторной отправки.
- Сохранить guard в handleSubmit: визуальная блокировка не заменяет проверку перед мутацией.
- Переиспользовать имеющийся disabled-стиль. Альтернатива — отдельный CSS-класс, но он дублирует стандартное состояние кнопки.
- Альтернатива — показывать текст ошибки после клика. Отклонена: не решает требование видимой недоступности до клика, добавляет не запрошенный интерфейс. Выданная спека не запрещает текст ошибки явно, но и не требует его.
- Альтернатива — только блокировать кнопку и удалить guard. Отклонена: ослабляет существующую защиту без необходимости.

## Risks / Trade-offs

- Проверка только в клиенте не защищает от прямого запроса к API → серверная валидация вне этой задачи; UI не отправляет пустые значения.
- Существующие пустые записи не исчезнут автоматически → проверять отсутствие новых мусорных записей на чистых тестовых данных.
- Ручная проверка студенткой в браузере не заменяется автоматической проверкой агентом → отмечать её отдельно и честно.
